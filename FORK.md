# Brainwires fork of webrtc-rs/rtc

This repository is [webrtc-rs/rtc](https://github.com/webrtc-rs/rtc) plus the changes listed
below. It is what ReachMyDevice pins, and what the Deno WebRTC extension (Brainwires/deno
`ext/webrtc`) builds on.

## Lineage

<!-- rtci-lineage:start -->
This project descends from webrtc-rs `rtc` ([webrtc-rs/rtc](https://github.com/webrtc-rs/rtc)); the last upstream commit merged is `0fbcaa74` (sync point below). It is developed independently. At 0.1.0 its crates were renamed from `rtc` / `rtc-*` to `rtci` / `rtci-*` (rtci: an RTC implementation) and the repository became `Brainwires/rtci`; statements about upstream below keep upstream's crate names. Upstream's licence and copyright notices are retained.

## Standing rules for syncing

1. **Never take an upstream change that removes, deprecates or disables a feature, API, flag or
   platform, or narrows behaviour by default.** If such a commit bundles a fix, port only the fix
   and revert the removal inside the merge resolution. Record it in the table below.
2. Every fork feature is kept unless upstream's version is a strict superset; when one is dropped
   for that reason, say so here.
3. Security fixes are always taken.

## Read this first: data channels to browsers carry at most 16 KB per message by default

RFC 8831 section 6.6: without user message interleaving (RFC 8260, I-DATA) "the sender SHOULD
limit the maximum message size to 16 KB". No current browser announces I-DATA, so toward a
browser `RTCSctpTransport::max_message_size` (W3C `maxMessageSize`) is 16384 and
`RTCDataChannel::send` refuses a larger message with
`Error::ErrMessageTooLargeWithoutInterleaving`, whose text names the limit and the setting.
Between two instances of this engine (both interleave) the limit is the peer's
`a=max-message-size`. To send larger messages to browsers, as browsers themselves do:
`SettingEngineBuilder::new().with_sctp_message_size_limit_without_interleaving(false)`. Details
under "Defaults the fork narrows on purpose" and in the `rtci::data_channel` module docs.

Left as the RFCs require: the TURN client accepts 401 (Unauthorized) and 438 (Stale Nonce) error
responses without MESSAGE-INTEGRITY (RFC 8489 §9.2.4; a server cannot sign a reply about the
credential or nonce it would sign with). So a forged 438 can still end the request it answers
with a stale-nonce error and replace the allocation's nonce; the server's own 438 on the next
request restores it. Only a sender that passes the server-address filter can do this, and it
cannot release the allocation or forge any other response. An unsigned 401 or 438 to a
permission refresh ends that refresh only: the permissions keep the time the server last
granted and are asked for again.

The same goes for what RFC 8489 section 9.2.5 has a client take from an unsigned 401 or 438:
the realm (a 401 naming another realm is answered with the key for that realm, once per
request, and the server's own 401 on that retry restores the realm), the password algorithm
among those the client accepts (`ClientConfig::password_algorithms` leaves MD5 out for a
deployment that never needs it) and whether the user name goes hashed (the nonce cookie that
says so is not authenticated, so a sender that passes the server-address filter can have the
user name sent in the clear, as it is to any RFC 5389 server). The one downgrade the RFC does
guard, PASSWORD-ALGORITHMS stripped from a response whose nonce cookie announces it, is
refused.

Also as the RFC has it: a success response to the first, unauthenticated Allocate is an
allocation (RFC 8656 section 7.2 step 1 lets a server ask for no credential). Nothing can sign
that response, so a sender that passes the server-address filter and knows the request's
transaction id can make the client believe in an allocation; requests for such an allocation
carry no credential until the server asks for one with a 401.

Key erasure (`conf/zeroize-1-dtls-srtp-key-erasure`, docs/key-erasure.md): every secret
`rtci-dtls`, `rtci-srtp` and `rtci-crypto` hold is overwritten before its memory is freed (the
DTLS 1.2 PRF and its outputs, master and premaster secrets, PSKs, key blocks, IVs, cookie and
ticket secrets, serialized state; the RustCrypto HMAC-SHA1 states and AES key schedules), the
stack is scrubbed after keyed objects are built, and secret keys come from the operating
system (`RTCRandom::fill_secret`). Checked by scanning every freed heap block and, on Linux, the
whole process. ring's own AEAD, header-protection and HMAC key objects, which ring does not
erase, are kept by the ring provider in an allocation of its own that is overwritten after the
drop.

### MSRV (fork only)

The workspace declares `rust-version = "1.89"`, inherited by every crate: the lowest toolchain
it builds on with every feature (uuid 1.29 needs 1.89; downstream ParolNet's MSRV is 1.91).
cargo.yml's `msrv` job checks the workspace on that toolchain with
`CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=fallback`, so a fresh resolution picks dependency
versions that support it. Raising it is a deliberate change of the manifest.

### Defaults the fork widens

- `configure_rtcp_reports` (and so `register_default_interceptors`) registers the RTCP session:
  all RTCP leaves in compound packets from the connection's SSRC, timed by RFC 3550 6.3 and
  RFC 4585 3.5, with a BYE on close. Register `SenderReportBuilder` / `ReceiverReportBuilder`
  at their slots instead to keep upstream's fixed-timer reports and bare feedback.
- `NackGeneratorBuilder` gives a lost packet up after ten requests or two seconds (upstream
  asks for ever); `with_max_nacks_per_packet(0).with_max_packet_age(None)` keeps upstream's.
- `register_default_interceptors` includes `KeyFrameRequestInterceptor`: an application on the
  defaults now receives the RTCP packets of a compound packet that carries a PLI or FIR as
  `RTCMessage::RtcpPacket`, each with the track it is about (upstream delivers no RTCP by
  default). Build the chain without it to
  keep upstream's behaviour.
- `register_default_interceptors` registers `configure_receiver_reference_time`: the default
  SDP offers `a=rtcp-fb:<pt> rrtr` on video, and a video stream's receiver sends RTCP XR
  receiver reference time blocks. Register the interceptors one by one without it to keep
  upstream's SDP.
- `MulticastDnsMode::QueryAndGather` without `multicast_dns_local_ip` hides every host candidate
  (upstream's points one name at 127.0.0.1 and hides none).
- `rtci-mdns` puts packets on the wire that upstream's never sent: two announcements for each
  local name, probes for a name that is not `<uuid>.local`, NSEC records, goodbyes on
  `close()`. `MdnsProbePolicy::Never` and `MdnsConfig::with_announce_count` are the knobs;
  announcing and goodbyes are what RFC 6762 requires and cannot be turned off.

- ICE, controlling agent: the pair it is nominating carries data until the nomination is
  answered or fails (RFC 8445 sections 12.1 and 12.2), so the peer, which selected that pair
  when the nomination reached it, has its DTLS handshake answered. Upstream sends and
  receives data only on the selected pair.

- BUNDLE fingerprints (jsep16): with a BUNDLE group only the tagged section's `a=fingerprint`
  lines (or the session level's) are read, as RFC 8859 section 4.5 says for the TRANSPORT
  category; the other bundled sections' are not compared. Upstream refused a description whose
  sections disagreed. `SettingEngineBuilder::with_bundled_fingerprints_agreeing(true)` keeps
  that refusal as a hardening.

- Remote tracks: `SettingEngineBuilder::with_source_departure_ends_track(true)` ends a remote
  track whose SSRCs all said BYE or timed out (RFC 8830 section 3); the default stays W3C
  webrtc-pc 9.3's muting. Upstream neither mutes nor ends.

- rtci-sdp reads descriptions in another character set named by `a=charset` (RFC 8866 section
  6.10) and relative `u=` references (section 9); upstream refused both.

### Defaults the fork narrows on purpose

- SDP (jsep15): remote descriptions without `c=` for a section, with an `a=imageattr` set
  that differs for one payload type across one BUNDLE group, or with two `ccm pause` lines for
  one payload type, are refused (RFC 8866 5.7, RFC 8859 4.7, RFC 7728 9); trickled candidates are grammar-checked (RFC 8839 5.1);
  application ICE credentials outside RFC 8839 5.4 and local reflexive candidates without
  `raddr` are refused; `create_offer` refuses a duplicate generated mid and ids that cannot be
  an msid. With BUNDLE the DTLS role is read from the tagged section. The browser fixtures
  (`tests/fixtures/browser-sdp/`, Chromium, Firefox, WebKit) pass all of it.

- SDP (jsep13): a remote description with an attribute that does not follow its grammar is
  refused, also when the value would be ignored (RFC 9429 section 5.8; upstream skipped such
  lines, or used them), except `a=msid` and `a=rid` lines, which RFC 8830 and RFC 8851 have
  ignored; an answer with `a=setup:actpass`, or one that flips the role of a continued DTLS
  association, is refused (RFC 5763 section 5, RFC 9429 section 5.8.3); bundled sections
  that give a payload type different `a=rtcp-fb` are refused (RFC 8859 appendix A). White
  space at the end of a value is tolerated by default for webrtc-rs 0.17.x, which ends an
  `a=rtcp-fb` without parameters with a space against RFC 4585 section 4.2 (fixed on
  webrtc-rs's default branch, `rtci` commit 718d405; Pion, which did the same, fixed it in
  v4.1.5, pion/webrtc#3207) (`with_strict_sdp_attribute_grammar(true)` refuses it). jsep14: real descriptions
  (`tests/fixtures/browser-sdp/`: Firefox, webrtc-rs 0.17; Chromium, Firefox and WebKit as
  the interop harness records them) are run through these checks, and a form a real writer
  uses that the strict grammar refuses must be a listed tolerance.
- SDP (jsep14): a later offer lists every available format (RFC 9429 section 5.2.2), not
  the formats of the last answer only (upstream offered the negotiated list once a kind was
  negotiated); the formats a remote answer accepts are negotiated without multi-codec
  negotiation too.
- RFC 7728 (jsep14): `set_parameters` turning an encoding off is a local pause (PAUSED sent)
  when pause and resume is negotiated (RFC 8853 section 5.2).
- Receiving before the answer (early1): upstream prepares its receivers when the answer is
  applied, so media that overtakes the answer is dropped. Here an applied local offer
  prepares each receiving section (formats, header extension ids, MID / rid / payload type
  demultiplexing, RTX mapping; RFC 3264 section 5.1, RFC 9429 sections 4.1.11 and 5.9), and
  early media goes straight to the receiver's track (W3C `[[Receptive]]`); the answer
  settles it and a rollback takes it back (`src/peer_connection/early_media.rs`). An initial
  offer still receives nothing before a remote description: no DTLS handshake runs without
  the peer's fingerprint (RFC 8842 section 5.2), so there the case is a provisional answer's.
  Formats newly offered get no RTCP feedback before the answer (RFC 4585 section 4.2).

- SDP (jsep12): a rollback with SDP contents is refused (RFC 9429 section 4.1.10; upstream
  ignored them; `with_rollback_content_ignored(true)` restores that); a later offer that stops
  multiplexing RTCP on a negotiated section is refused under every mux policy (RFC 9429
  section 5.8.3).

- SDP (jsep-43): a remote description whose bundled sections give one payload type two codec
  configurations is refused (RFC 9143 section 9.1.1; upstream applied it); a remote FlexFEC
  format without `repair-window`, or with one longer than the registered one, is not
  negotiated (RFC 8627 sections 5.1, 5.2.1); FlexFEC registered without a window is offered with
  10 s.

- SRTP (`rtci-srtp`), each following RFC 3711 where upstream does not: a `Context` created without
  replay options has a 64-packet replay window (upstream: none; pass
  `srtp_no_replay_protection()`); `srtp_replay_protection(n)` / `srtcp_replay_protection(n)`
  refuse n below 64 (section 3.3.2); the first SRTCP index is 0, not 1 (section 3.4); a master key
  is refused after its lifetime (section 9.2), which is 2^31 packets for the AES-192 / AES-256
  counter-mode suites (RFC 6188 section 4; `Context::set_key_lifetime` changes it).

- DTLS: the default WebRTC cipher suites are AEAD only (AES-128-GCM, ChaCha20-Poly1305); the
  AES-256-CBC-SHA suites are opt-in. This is the one deliberate exception to rule 1, decided by
  the maintainer for security. To offer CBC again, list the suites with
  `SettingEngineBuilder::with_dtls_cipher_suites` (for example
  `CipherSuiteId::Tls_Ecdhe_Ecdsa_With_Aes_256_Cbc_Sha`).
- Codecs: `register_default_codecs` no longer offers ULPFEC (`video/ulpfec`, PT 116). Nothing
  in the engine encodes or decodes RFC 5109 FEC (and RED, which carries it from browsers, was
  never offered), so offering it invited repair packets that were dropped: a claim the engine
  did not keep. This takes upstream's `4d0c5070` (#837), which the fork had reverted under
  rule 1; the maintainer decided the exception. An application with its own coder registers
  `MIME_TYPE_ULP_FEC` itself. RED + ULPFEC receive is planned work, not a default.
- Codecs: `MediaEngine::register_codec` refuses a payload type of 64 to 95, and a remote format
  numbered so is not used (RFC 5761 section 4: such a packet with the marker bit set has the
  second octet of an RTCP packet, and the engine always multiplexes RTP and RTCP). No switch:
  the demultiplexer cannot be told otherwise.
- BUNDLE: answers and subsequent offers repeat the BUNDLE attributes in every bundled m=
  section, against RFC 9143 section 7.1.3 (tagged section only), because Chromium, WebKit and
  Firefox refuse the RFC form ("rtcp-mux must be enabled when BUNDLE is enabled"; "m-section
  at level 1 is missing a=rtcp-mux"); `with_bundle_attributes_repeated(false)` writes the RFC
  form. `RTCBundlePolicy::MaxBundle` is `must-bundle` (W3C webrtc-pc section 4.2.5 defines
  the name; RFC 9429 section 4.1.1's SHOULD, ignoring it, is
  `with_max_bundle_as_must_bundle(false)`), and an initial offer needs `a=rtcp-mux` in each
  bundled section that is not bundle-only (RFC 9143 section 9.3.1.1). Maintainer rule of
  2026-11-22: the RFC behaviour is the default unless a browser cannot connect under it; then
  the RFC form is the setting.
- Simulcast: no pause mark `~` in `a=simulcast` (RFC 8853 section 5.2: it needs RFC 7728,
  which the engine does not implement); upstream writes it for an inactive encoding and echoes
  it from offers, as libwebrtc does: `with_rid_pause_marks(true)`. An answer no longer adds
  `send` rids the offer did not ask for, and an applied answer prunes the sender's encodings
  to the ones it accepted (RFC 8853 section 5.3.2 / 5.3.3, W3C "set a session description").
  A local rid must be 1 to 255 alphanumerics (RFC 8852 section 3.1); no switch.
- BUNDLE, IDENTICAL attributes (jsep16): a remote description whose bundled sections carry an
  attribute of RFC 8859's IDENTICAL category (`a=rtcp-rsize`, `a=ecn-capable-rtp`,
  `a=extmap-allow-mixed`, ...) with different values is refused (RFC 8859 section 4.3). An absence is not: the tagged
  section speaks for the group. No browser description recorded by the interop harness breaks
  the rule. An offer whose bundled sections list different ECN methods used to be answered
  with the tagged section's; no switch.
- Codecs: an encoding's codec is matched with the W3C codec dictionary match (webrtc-pc
  5.4): no mime-type-only fallback (upstream's `codec_parameters_fuzzy_search` partial
  match), and setCodecPreferences / setParameters compare every format parameter.
- SCTP: a peer connection's association schedules its streams by weighted fair queueing
  (RFC 8831 section 6.4) and announces user message interleaving (RFC 8260), the zero checksum
  (RFC 9653) and a State Cookie with a MAC, each of which upstream leaves off or lacks;
  `with_sctp_weighted_fair_queueing(false)`, `with_sctp_message_interleaving(false)` and
  `with_sctp_zero_checksum(false)` are upstream's behaviour.
- Data channels: on an SCTP association that does not interleave user messages (RFC 8260),
  which is every association with a current browser, `send` refuses a message over 16 KB
  (`Error::ErrMessageTooLargeWithoutInterleaving`, which names the limit and the setting) and
  `maxMessageSize` says 16384 (RFC 8831 section 6.6, SHOULD). Upstream, like the browsers,
  sends up to the peer's `max-message-size`. Maintainer rule of 2026-11-22: the RFC behaviour is
  the default, the browsers' a setting
  (`SettingEngineBuilder::with_sctp_message_size_limit_without_interleaving(false)`). The SCTP
  packet size is likewise smaller than upstream's over IPv4 (1135 bytes against 1191 under
  DTLS 1.2, 1150 under DTLS 1.3: RFC 8831 section 5), unless `with_sctp_mtu` sets it.
- `rtci-mdns`: an unanswered query ends after 30 seconds by default (upstream: never) and is
  retried at doubling intervals from one second (upstream: every `query_interval`, any
  value). `MdnsConfig::without_query_timeout` keeps a query alive; the interval floor is RFC
  6762 section 5.2 and has no switch. A name with more than one address does not resolve
  (`MdnsConfig::with_multiple_addresses(true)` takes the first, as upstream does).
  `MIME_TYPE_ULP_FEC` itself. RED + ULPFEC is now implemented as opt-in interceptors
  (`configure_ulpfec`, `rtci-interceptor/src/ulpfec/`); it is still not a default codec.
  jsep17 re-examined it: the reason "nothing in the engine encodes or decodes it" no longer
  holds for the coder, but `configure_ulpfec` took fixed payload types rather than the
  negotiated ones (since media-25 the sender takes the negotiated ones), and no browser interop cell exercises ULPFEC in RED, so nothing shows the
  default would interoperate: video `red` + `ulpfec` stay out of the defaults. Audio RED
  (Opus in Opus) is a default since jsep17.

## How to sync with upstream

```sh
git clone https://github.com/Brainwires/rtci.git && cd rtci
git remote add upstream https://github.com/webrtc-rs/rtc.git
git fetch upstream
git switch -c sync/upstream-<version> master
git log --oneline "$(git merge-base master upstream/master)"..upstream/master   # audit these
git merge --no-ff upstream/master
```

1. Audit every new upstream commit against the standing rules above, before resolving. For
   each removal or narrowed default, plan how the resolution keeps the old behaviour.
2. Resolve the conflicts. Keep fork features, port bundled fixes from commits you leave out, and
   add a row to the tables above for each.
3. Build and test with the pinned toolchain:
   `RUSTUP_TOOLCHAIN=1.92.0 cargo build --workspace && cargo test --workspace --no-fail-fast`.
4. Update the sync point at the top of this file, then open a PR into `master`.
