# Specification issues: defects found in the specifications during the audit

The clause-by-clause audit (`audit/*.md`) checks the engine against the specifications. On the
way it found problems in the specifications themselves. This file lists them in one place, one
row per distinct problem, with what rtci does about each one and what the maintainers upstream
have done.

**What counts:** a defect in a specification's text, a contradiction between two specifications
(or two sentences of one), a specification against its own test suite (web-platform-tests), a
requirement no test can observe, or an obsolete reference that changes a requirement or how the
audit cites it. **What does not count:** our own bugs, and browser bugs with no specification
angle. Departures by decision with no defect in the text (RFC 9429 5.11 feedback, RFC 8083
packet size, RFC 5764 section 3: `draft-work.md` rows 15, 17 and 19) are not listed.

Where a row is also in the draft-work register ([draft-work.md](draft-work.md)), the register
holds the analysis, the quotes in full and the dated draft work; the row here links it as
"register #n" instead of repeating it. "Engine" is `conf/train-36` (33753b91) unless a branch
is named, as in the register. Upstream states were read on 2026-11-27 (rfc-editor.org
`errata.json` and RFC metadata; GitHub issues and pull requests of `w3c/webrtc-pc`,
`rtcweb-wg/jsep`, `tlswg/dtls13-spec`, `web-platform-tests/wpt`; the live editor's draft, `main`
65be6fa5 of 2026-11-12) unless the row gives another date. "None found" means nothing was found
in those places on that date. Quotes are as they stand in the audit files, the register, the
handoff notes or the coordinator's reference copies of the texts (`specs/`, `specs-extra/`).

Classes: `contradiction` (two normative texts, or two sentences of one, cannot both be met),
`text-vs-intent` (merged text does not do what the issue it closed decided), `text-vs-test` (a
web-platform test or other conformance test contradicts the text), `ambiguous` (the text admits
more than one reading, or leaves a step undefined), `unobservable` (a MUST no test can observe),
`stale-reference` (an obsolete or superseded reference that changes a requirement or how the
audit cites it), `erratum-pending` (an erratum is filed and not acted on).

## How this list is kept

A row is added when an audit note, a handoff note or the draft-work register records a defect
in a specification's text (the classes above); the row cites where it was recorded. The list is
re-checked before each release together with `draft-work.md` (`docs/releasing.md`, "Before"):
for each row, read the errata list, the issues and pull requests named and the editor's
draft; update the dates; when upstream resolves a row, keep it with the resolution until the
engine follows, then remove it in the release that does. When the owner files an item, its
"Filed by us?" cell names the erratum or issue number.
