# RFC 8830: WebRTC MediaStream Identification in the SDP: clause audit

Spec: RFC 8830, January 2021. Audited at fork master 8916bc3. The RFC has four capitalised clauses; the
procedures of sections 2 and 3 are written in lower case and are listed at MUST level where they describe
what a sender writes or a recipient does.

Path legend: `sdp/mod.rs` = `src/peer_connection/sdp/mod.rs`, `pc/` = `src/peer_connection/`.

## Gaps, in order of importance

1. **msid without appdata; several msid lines (S).** RFC8830-3-5, 2-2, 3-4.
2. **Track lifetime from SDP (M).** RFC8830-3-7, 3.2.5-1, 3-9, 3-8: end (and report) a remote track when
   its msid disappears; move a track between streams without replacing it; RTP timeout.
3. **Peers that send no msid (M).** RFC8830-3.1-1, 3.1-2, 3.1-3: default stream, track per section from
   the first RTP packet, a signal for discarded early media.
4. **Stream model (M).** RFC8830-3-6, 3.2.2-1: a list of stream ids per remote track and events for
   stream changes; apply on the offer, not only on the answer.
5. **`-` and syntax (S).** RFC8830-3-1, 2-1, 2-4: write `a=msid:- <track>` for a streamless sender; check
   ids are 1 to 64 token characters when a track is added.

## Bugs found

- **RFC8830-3-5:** `a=msid:stream` (no appdata) is ignored (`src/peer_connection/sdp/mod.rs:475`).
  Reproduce: remote offer with `a=sendrecv`, `a=msid:s1` and no `a=ssrc` lines; after the answer is
  applied the receiver has no track, and RTP for the section is never delivered.
- **RFC8830-2-2:** with `a=msid:s1 t1` and `a=msid:s2 t1`, the track's stream id is `s2`; `s1` is lost.
- **RFC8830-2-1:** a local stream id containing a space (`MediaStreamTrack::new("my stream", ...)`) is
  written verbatim, producing `a=msid:my stream track`, which no parser reads as intended.
