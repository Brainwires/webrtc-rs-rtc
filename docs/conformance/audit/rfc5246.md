# RFC 5246 conformance audit: TLS 1.2, as DTLS 1.2 relies on it

Spec: RFC 5246, August 2008 (obsoleted by RFC 8446; still the base of DTLS 1.2, RFC 6347). ECDHE rows follow RFC 8422 (August 2018), which replaces the RFC 4492 the crate documentation cites.
RFC 9846 (TLS 1.3, July 2026) obsoletes RFC 5246 and RFC 8422 (and RFC 8446); the rows keep RFC 5246's and RFC 8422's section numbers, which DTLS 1.2 (RFC 6347) still cites.

Audited at fork master 8916bc3. Scope: the record protection, alert and handshake rules DTLS 1.2 inherits (sections 4.7, 5, 6, 7, 8.1, 9, A.5, E, F.1.1.3), and RFC 8422 as far as the offered suites need it. Suites the crate implements: ECDHE_ECDSA and ECDHE_RSA with AES_128_GCM_SHA256, CHACHA20_POLY1305_SHA256, AES_256_CBC_SHA; ECDHE_ECDSA with AES_128_CCM and CCM_8; PSK with AES_128_GCM_SHA256, AES_128_CCM, CCM_8. The engine offers ECDHE_ECDSA_AES_128_GCM, ECDHE_RSA_AES_128_GCM and ECDHE_ECDSA_CHACHA20_POLY1305 (`src/peer_connection/transport/dtls/mod.rs:30`). Not audited: RFC 4279 (PSK), RFC 5288/6655/7905 beyond the nonce and additional-data rows. Rows marked "Implicit" have no keyword in the text. Clauses the DTLS specification replaces are `n/a` with the replacing section.

## Session resumption (`conf/ice-12-dtls12-resumption`)

RFC5246-7.3-3 is implemented in `rtci-dtls`, as specified here before: a server session cache
(`session::SessionCache`, `MemorySessionCache`: session id to master secret, suite, extended
master secret flag, peer certificates, server name, lifetime, bounded, zeroized as sessions
drop, forgotten when a connection fails), the abbreviated flights (`Flight4b`: ServerHello,
NewSessionTicket, ChangeCipherSpec, Finished; `Flight5b`: the client's ChangeCipherSpec and
Finished, the last flight, sent again when the server's comes again), RFC 7627 section 5.3 on
both sides, RFC 5077 tickets sealed by the DTLS 1.3 `TicketIssuer` (a version byte and
additional data of their own), and a client keeping its sessions in the `SessionStore` of the
DTLS 1.3 work. The cookie exchange runs for a resumption as for any handshake (RFC 6347 4.2.1:
the server MAY skip it, and does not). A session made without the extended master secret is
never kept, and PSK suites are not resumed. The peer connection configures no cache, no tickets
and no store: WebRTC authenticates each association by its SDP fingerprints.

## Gaps, in order of importance

1. **Server-side Finished verification (S).** RFC5246-7.4.9-2 (and the missing negative test for the
   client side, 7.4.9-1). Compute `prf_verify_data_client` over the transcript in `Flight4::parse` and
   compare in constant time; fail with decrypt_error. See bug 1.
2. **Hello parsing (S).** RFC5246-7.4.1.2-1, -7.4.1.2-6, -7.4.1.2-7, -7.4.1.3-4. Skip session_id bytes,
   accept hellos that end before the extensions block, reject trailing bytes with decode_error, check
   the ServerHello compression method. Bugs 2 and 3.
3. **Extension discipline (S).** RFC5246-7.4.1.4-1, -7.4.1.4-2, -7.4.1.4-4, RFC 8422 5.2. Record which
   extensions the ClientHello carried; echo only those in ServerHello (never supported_groups); a
   client aborts with unsupported_extension on anything it did not send. Bug 4.
4. **signature_algorithms negotiation (M).** RFC5246-7.4.1.4.1-2, -7.4.1.4.1-4, -7.4.2-4, -7.4.3-1,
   -7.4.3-2, -7.4.4-2, -7.4.8-2. Server: intersect the client's list with the key's schemes before
   picking the suite and the ServerKeyExchange scheme. Client: honour CertificateRequest's list and
   certificate types for the certificate and CertificateVerify. Bug 7.
5. **Record size limits (S).** RFC5246-6.2.1-1, -6.2.1-2. Refuse writes above 2^14; refuse received
   records above 2^14 + 2048.
6. **Alert descriptions (S).** RFC5246-7.2.2-7 (stop sending no_certificate), -7.2.2-8, -6-2, -7.4-2
   (unexpected_message for an out-of-order message instead of a stall).
7. **Curve negotiation failure (S).** RFC 8422 5.1: fail with handshake_failure when the client's
   supported_groups has no curve in common. Bug 12.
8. **Version tolerance (S).** RFC5246-E.1-2, -E.1-4: answer an unknown higher ClientHello version with
   DTLS 1.2 rather than refusing it. No deployed client needs it today.
9. **Secret hygiene (S).** RFC5246-7.2.2-1: zeroize master secret, premaster secret and key block
   when an association ends or fails (`State` holds them as `Vec<u8>`).
10. **Session resumption (L, MAY).** RFC5246-7.3-3. Done (`conf/ice-12-dtls12-resumption`), see
    "Session resumption" above.
11. **Tests for the `untested` rows (M).** Known-answer vectors for GCM and ChaCha20 record
    protection, a mixed unknown/known cipher-suite list, early application writes, fatal alert level.

## Bugs found

1. **The server never checks the client's Finished.** `rtci-dtls/src/flight/flight4.rs:467` pulls the
   Finished message and only tests that it parsed; `flight6.rs:33` likewise. The client side does
   check (`flight5.rs:136`). The record is AEAD-protected, so the client must hold the keys, but the
   transcript is not confirmed to the server: a ClientHello altered in transit (suite list, SRTP
   profiles, extensions) is noticed only by the client, after the server has already declared the
   handshake complete, exported SRTP keys and started sending. Reproduction (no network): drive a
   client and a server `DTLSConn`; before the client generates Flight 5, set
   `client.state.local_verify_data = vec![0; 12]` (generate reuses a non-empty cached value,
   `flight5.rs:508`); feed the flight to the server; `server.is_handshake_completed()` is true.
   Expected: fatal decrypt_error and a failed association.
2. **A ClientHello with a non-empty session_id is misparsed.**
   `rtci-dtls/src/handshake/handshake_message_client_hello.rs:157`. Reproduction: marshal a
   ClientHello, insert `20` + 32 bytes after the random; `unmarshal` reads the first session byte as
   the cookie length and returns an error or garbage suites. Peers that offer a session id (OpenSSL
   with a cached session, some embedded stacks) cannot connect. `ServerHello` parsing does it right
   (`handshake_message_server_hello.rs:121`).
3. **Hellos without an extensions block are dropped.** `handshake_message_client_hello.rs:175`,
   `handshake_message_server_hello.rs:131`. Reproduction: marshal a ClientHello with no extensions
   and cut the last two bytes (fix the header lengths); the server never answers. Every in-tree test
   builds hellos through `marshal`, which always writes the two length bytes.
4. **ServerHello carries extensions the client did not send.** `rtci-dtls/src/flight/flight4.rs:563`.
   Reproduction: ClientHello with only signature_algorithms; the ServerHello holds
   renegotiation_info, supported_groups and ec_point_formats. A strict client (RFC 5246 7.4.1.4)
   aborts with unsupported_extension; supported_groups in a TLS 1.2 ServerHello is defined nowhere.
7. **Signature algorithm lists from the peer are ignored.** Server: `flight4.rs:660`; client:
   `flight5.rs:415`, `flight3.rs:315`. Reproduction: a client offering only
   `ecdsa_secp384r1_sha384` against a P-256 certificate server still gets a SHA-256
   ServerKeyExchange signature instead of a handshake failure (or a suite that fits).
11. **The reserved alert no_certificate(41) is sent.** `flight4.rs:133`, `:512`, `:534`.
    Reproduction: `RequireAnyClientCert` server, client with no certificate; the alert on the wire
    is `02 29`.
12. **No common curve is not an error.** `rtci-dtls/src/flight/flight0.rs:162`. Reproduction:
    ClientHello whose supported_groups lists only secp521r1; the server sends a ServerKeyExchange
    on its default curve instead of handshake_failure.

Lower severity, no separate number: the client's Finished comparison (`flight5.rs:154`) and the
cookie comparison (`flight2.rs:86`) are not constant time.
