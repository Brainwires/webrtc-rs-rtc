# RFC 9147 conformance audit: Datagram Transport Layer Security version 1.3

Spec: RFC 9147, April 2022 (obsoletes RFC 6347). One row per normative sentence of sections 4 to 11 (the text of the clause, cut to 25 words), plus rows marked "Implicit" for wire formats and state machines the text states without a keyword. The TLS 1.3 clauses DTLS 1.3 inherits are in `rfc8446.md`; the connection id for DTLS 1.2 is in `rfc9146.md`.

DTLS 1.3 is implemented in `rtci-dtls/src/dtls13/` (branches `conf/dtls13-1` to `conf/dtls13-6`): the record layer, the handshake with certificates, ACKs and retransmission, key update, connection ids. Tests are in that directory (`record_test.rs`, `key_schedule_test.rs`, `handshake_test.rs`, `reliability_test.rs`, `connection_id_test.rs`, `openssl_kat_test.rs`); the last reproduces handshakes recorded with OpenSSL 4.1.0, and `rtci-dtls/examples/dtls_interop.rs` was run against `openssl s_server` and `s_client` (`-dtls1_3`, `-dtls1_2`, `-dtls`) in both roles. Pre-shared keys (`conf/dtls13-10-psk`): session tickets and resumption, external PSKs, `psk_dhe_ke` by default and `psk_ke` as an option (`dtls13/psk.rs`, `session.rs`, `psk_test.rs`); the peer connection of the `rtci` crate keeps them off. Post-handshake authentication (`conf/dtls13-11-post-handshake-auth`): `Endpoint::request_client_certificate`, `post_handshake_auth_test.rs`. 0-RTT (`conf/dtls13-12-early-data`): `Endpoint::connect_with_early_data`, `ConfigBuilder::with_max_early_data`, `early_data_test.rs`; off by default.

## Gaps, in order of importance

1. **PSK: done (`conf/dtls13-10-psk`).** RFC 8446 sections 2.2, 4.2.9, 4.2.11, 4.6.1 and C.4 (see `rfc8446.md`), RFC9147-5.8.4-1. Tickets are AES-256-GCM sealed by the server under a key its configuration makes at random, carry the resumption PSK, the suite, the issue time (milliseconds from the first `now` the configuration was given: the engine reads no clock), the lifetime, `ticket_age_add`, the server name and the peer's certificate chain, and are accepted once (a record of the accepted ones until they expire, at most 65536). A client keeps them in a `SessionStore` by server name and takes one per ClientHello. The binder is computed over the ClientHello as written (DTLS 1.3 transcript form) and again after a HelloRetryRequest. A resumed handshake has no Certificate or CertificateVerify; the certificates of the handshake the ticket came from are reported and the configured peer-certificate check runs on them again. In the peer connection all of it stays off (WebRTC authenticates each association by the fingerprints of its SDP): `the_peer_connection_neither_sends_nor_accepts_session_tickets`.
2. **Post-handshake authentication: done (`conf/dtls13-11-post-handshake-auth`).** RFC 8446 sections 4.2.6, 4.3.2, 4.6.2, RFC9147-5.8.4-2. A client configured with `with_post_handshake_auth` sends the extension; a server's `request_client_certificate` sends a CertificateRequest with 16 random bytes of context (up to four unanswered); the client answers at once with Certificate, CertificateVerify and Finished in one post-handshake flight (an empty Certificate and Finished when it has no certificate the request allows), the Finished keyed from its current application traffic secret; the server checks them in order as it checks a client certificate in the handshake and reports `EndpointEvent::PeerAuthenticated`. Off in the peer connection (it authenticates the client in the handshake). Open: a KeyUpdate of the client sent but not yet acknowledged while it answers leaves the two sides with different secrets for that Finished (RFC 8446 does not settle which N is meant then); the answer fails with decrypt_error.
3. **0-RTT: done (`conf/dtls13-12-early-data`), off by default.** RFC 8446 sections 2.3, 4.2.10, 4.6.1-15/-16, 8, E.5; RFC9147-5.6-1. A client connects with `Endpoint::connect_with_early_data`: with a ticket of its store that allows that much, the data goes after the ClientHello in one epoch 1 record under `client_early_traffic_secret`, and `State::early_data_accepted` says what the server did with it. A server with `with_max_early_data(n)` issues tickets that allow n bytes and takes 0-RTT data only for the first identity, a ticket of this configuration used for the first time (RFC 8446 section 8.1: the record of accepted tickets), of the same suite, in a first ClientHello, whose age agrees with the server's within ten seconds (section 8.3); it delivers it as `EndpointEvent::EarlyData` before the handshake completes, ends the association on more than n bytes, and drops the epoch 1 keys with the first record of epoch 3. External PSKs get no 0-RTT (no single-use record exists for them). A HelloRetryRequest rules 0-RTT out, so with the cookie exchange on (the default) none is taken; the MAY of RFC9147-5.1-9 (no cookie exchange for a PSK whose address is known) is not taken. The anti-replay record lives in the server configuration: servers that share tickets would need a shared record, and the ticket key is per configuration, so another instance cannot open them at all.
4. **Persistently bad peers: decided, opt-in (`conf/dtls13-10-psk`).** RFC9147-5.10-2 stays `partial`: the limit exists (`with_invalid_record_limit`) and is off by default, because the records it counts are unauthenticated and a default limit would let anyone who knows the address end the association, against the fork's hardening against unauthenticated teardown.
5. **Tests for implemented rows (S each).** The `untested` rows: the epoch limit of key updates (4.2.1-5, 6.1-2, 8-5, 8-7), ten records per transmission (5.8.3-1), the fatal alert repeated (5.10-1), a new association on a live address under DTLS 1.3 (5.11), the measured timer (5.8.2-7), MTU backoff (4.4-13).
