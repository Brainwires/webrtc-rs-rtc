Spec: RFC 7675, October 2015. Audited against fork master 8916bc3.
Code: `rtci-ice/src/agent/mod.rs` (`validate_selected_pair`, `check_keepalive`,
`handle_inbound`), `rtci-ice/src/agent/agent_selector.rs`, `src/peer_connection/handler/ice.rs`.

Totals (21 rows; `MUST (proc)` rows are behaviour the RFC states without a keyword and count
as MUST):

- MUST: tested 14 / untested 0 / partial 0 / missing 0 / violated 0 / n-a 1
- SHOULD: tested 2 / untested 0 / partial 0 / missing 0 / violated 0 / n-a 2
- MAY: tested 0 / untested 0 / partial 0 / missing 0 / violated 0 / n-a 2

How it works here: the keepalive of RFC 8445 §11 is a Binding request on the selected pair
every `keepalive_interval`. A success response to one of those requests, authenticated and
matched by transaction id and destination, sets `Candidate::last_consent`; a request's
transaction is open for `Rm` (16) times the pair's RTO (8 s at least, 30 s at most), so the
response may come long after later requests were sent. With no such
response for `disconnected_timeout` (5 s) the agent is `Disconnected`, and after
`disconnected_timeout + failed_timeout` (5 + 25 = 30 s) it is `Failed`, which drops the
selected pair and with it the media path; when the end of the candidates has not been
indicated yet (W3C webrtc-pc 5.6.4, ice-32) it stays `Disconnected` and only the pair is
dropped, removed and no longer answered. Tests are in `rtci-ice/src/agent/` unless a path is
given.

## Gaps, in order of importance

1. **WP-CONSENT-1: the consent timer (S).** Default period 5 s, each interval drawn from
   0.8 to 1.2 of it with the crypto provider's RNG, a floor of 4 s on the configured value
   (5.1-3, 5.1-4, 5.1-5). Fix the `keepalive_interval` doc comment. Needs `poll_timeout` to
   return the jittered deadline rather than a fixed tick. Tests: interval bounds over many
   draws, a configured 1 s is raised or refused, two consecutive requests differ in
   transaction id (5.1-6).
2. **WP-CONSENT-2: consent during an ICE restart (M).** Keep the old pair, its remote
   candidate and the old credentials alive beside the new generation, keep sending consent
   requests on it and drop `previous_media_path` when 30 s pass without a response (5.1-11,
   5.1-2). Today a restart is the one time data flows unchecked.
3. **WP-CONSENT-3: the 30 s bound (S).** Consent expiry is `disconnected_timeout +
   failed_timeout`, which the application can stretch or switch off. Either cap the sum at
   30 s for the purpose of stopping transmission or separate "consent expired" from the
   W3C `failed` timer (5.1-2). Clear `pending_binding_requests` on expiry (5.1-9). Refuse
   reuse of the lost session's credentials (5.1-15).
4. **WP-CONSENT-4: response wait from RTT (S).** Replace the fixed 4 s with a bound derived
   from the pair's measured RTT (5.1-7). Belongs with the STUN transaction work of
   `rfc8445.md` WP-ICE-1.
5. **WP-CONSENT-5: tests (S).** Consent expiry on a TCP pair (5.1-12); no data leaves after
   `Failed` at the peer-connection level.

## Bugs found

Fixed on `conf/ice-2-consent`, each with the test named in its row: 1, 2, 3. (The totals line
above counted one "partial" MUST that the table has as "tested"; it is recounted from the
rows.)

What "Disconnected" means changed with the interval: consent requests are now 4 to 6 seconds
apart, so "no response for `disconnected_timeout` (5 s)" would be true between two answered
requests. The agent is Disconnected when a consent request has been unanswered for
`disconnected_timeout`, which is 9 to 11 seconds after the last response by default (it was 5).

Documented behaviour (coordinator's decision, 2026-11-25; measured with the capacity instrument):
ONE lost consent datagram can make the agent Disconnected for a moment. A consent request "is
transmitted once only", the next one follows 4 to 6 seconds later (the period may not be under
4 seconds, the intervals are randomized: the agent may not retry sooner), and the agent is
Disconnected 5 seconds after a request no response has followed. So when a request or its
response is lost and the next interval drawn plus the round trip is over 5 seconds (about half
the draws), the agent reports Disconnected until the next answer: for the interval plus the
round trip less 5 seconds. Measured through a capacity collapse (2.5 Mbit/s to 300 kbit/s
behind a 300 ms drop-tail queue, where the STUN datagram meets the full queue in the overload;
STUN is not paced and shares the media's 5-tuple): a peer leaves Connected in 13 to 17 % of
calls (128 of 1000 on the tree measured; 35 % with both directions capped, 56 % with 5 % loss
on the reverse path all call long), every time after a lost consent datagram, for 0.2 to 1.4 s
(median 0.5 s); none stays disconnected, none fails (`disc_max`, `disc_open`, `stun_lost` of
`tests/capacity_instrument.rs`). W3C webrtc-pc 5.6.4 calls the state "transient ... may
trigger intermittently (and resolve itself without action) on a flaky network. The way this
state is determined is implementation dependent", with "Repeatedly failing to receive a
response to STUN requests" as an example; libwebrtc takes 5 unanswered pings and 5 seconds
(`p2p/base/connection.cc`, `kConnectionWriteConnectFailures`, `kConnectionWriteConnectTimeout`),
with pings 0.48 to 2.5 seconds apart, which RFC 7675's 4-second floor does not allow an agent
that uses the consent checks for it. The rule stays one request and 5 seconds: an application
should treat a short `disconnected` as the transient the specification describes.

1. **Consent checks are sent every 2 s, with no jitter** (`rtci-ice/src/agent/agent_config.rs:15`,
   `rtci-ice/src/agent/mod.rs:1285`). The RFC forbids a period under 4 s and requires
   randomization. Reproduce: connected pair, default configuration, advance virtual time by
   60 s and count Binding requests on the selected pair: 30, evenly spaced; expected 10 to 15
   with intervals spread over 4 to 6 s.
2. **Data flows without consent during an ICE restart**
   (`rtci-ice/src/agent/mod.rs:973-997`). Reproduce: connect two agents, `apply_restart` on
   one and never give it remote credentials (the peer has gone away); with `failed_timeout`
   0 `media_path()` stays `Some` for ever, and with defaults it stays for the whole checking
   timeout although no response has arrived on that path since the restart. Expected: the
   path ends 30 s after the last consent response.
3. **`AgentConfig::keepalive_interval` is documented as defaulting to 10 seconds**
   (`rtci-ice/src/agent/agent_config.rs:123-126`); the constant is 2 s.
4. **A path whose round trip rose above the consent wait lost its consent with every request
   answered** (`rtci-ice/src/agent/agent_selector.rs`: `consent_wait`, `run_transactions`,
   `handle_inbound_binding_success`, `handle_success_response`, at master d914b929; also in
   0.1.0). The wait was four times the pair's last round-trip time, clamped to 500 ms .. 4 s.
   At its end the transaction was removed (`run_transactions`), so the answer found no
   transaction ("discard message [...] unknown TransactionID") and neither renewed consent nor
   gave a round-trip time: the wait never adapted. Seen in a simulated call whose uplink was
   capped behind a 1000 ms queue (hosted runs 45493039743 and 45493049553): four consent
   requests answered after 785, 523, 608 and 918 ms, `Disconnected` 5 s after the first of
   them was sent, `Failed` 30.01 s after the last answer that came within 500 ms. A pair whose
   round trip is over 500 ms from the first check failed 30 s after it was selected when all
   its checks had been retransmitted (a retransmitted request gives no round-trip time); with
   a peer whose own requests trigger checks, one of them is usually cancelled before its
   retransmission and answered, which gave a round-trip time and hid the defect. Rows 5.1-2 and 5.1-7 said `tested` while this was so: 5.1-2's tests were of
   silent pairs only, and 5.1-7's test asserted the defect (a response 400 ms into the next
   interval "gives no consent"). Fixed on `conf/ice-26-consent-late-responses`: 5.1-7, 5.1-16.
   Reproduce: connect two agents, raise the one-way delay to 300 ms and more, lose nothing,
   wait 30 s (`tests/ice_consent_slow_path_rtc2rtc.rs`: three of its four tests fail on
   master, hosted run 45501729474).
