# RFC 8445: Interactive Connectivity Establishment (ICE), clause audit

Spec: RFC 8445, July 2018 (obsoletes RFC 5245). Audited against fork master 8916bc3.
Code: `rtci-ice/`, `src/peer_connection/handler/ice.rs`, `src/peer_connection/transport/ice/`,
role selection in `src/peer_connection/mod.rs`.

Totals (221 rows; `MUST` includes MUST NOT and the 60-odd `MUST (proc)` rows, `SHOULD` includes
RECOMMENDED / NOT RECOMMENDED; a row with two keywords counts under the first):

- MUST: tested 135 / conflict 1 / untested 0 / partial 0 / missing 0 / violated 0 / n-a 20
- SHOULD: tested 24 / untested 0 / partial 0 / missing 0 / violated 0 / n-a 25
- MAY: tested 9 / untested 0 / partial 0 / missing 2 / violated 0 / n-a 5

Reading notes:

- Level `MUST (proc)` marks a behaviour the RFC states as procedure without a BCP 14 keyword
  (state machines, formulas, "the agent sets ..."). They are counted with MUST: an ICE agent
  that skips them is not an RFC 8445 agent, whatever the keyword count says.
- The agent is sans-I/O and gathers nothing: the application opens sockets, runs STUN / TURN
  and hands candidates to `RTCPeerConnection::add_local_candidate`. Gathering clauses are
  `n/a` with that reason; clauses about the candidate list the engine then owns (priority,
  foundation, redundancy) are judged.
- At the audit the engine had one transport (BUNDLE only, rtcp-mux only): one data stream, one
  component, one checklist. Since mt-2 a section outside a BUNDLE group, and each BUNDLE group,
  is a transport with an ICE agent of its own (`docs/conformance.md`, "Several transports"):
  several data streams, each with its own checklist; every transport is rtcp-mux only (one
  component). Clauses that only order several checklists of one agent stay `n/a` (each
  transport's agent has one); clauses that also bind one checklist (Frozen state,
  foundations, pacing) are judged.
- Paths are relative to the repository root. Tests are in `rtci-ice/src/agent/` unless a path
  is given.

## Gaps, in order of importance

1. **WP-ICE-1: the checklist of RFC 8445 (XL).** One work package, because the pieces depend
   on each other: a checklist sorted by the correct pair priority (6.1.2.3-1, -2), pair
   pruning with reflexive locals replaced by their base (6.1.2.4-1, -2), the Frozen state and
   foundation-based unfreezing (6.1.2.6-1, -2, 6.1.4.2-3, 7.2.5.3.3-2), the triggered-check
   FIFO (6.1.4.1-1, 6.1.4.2-2, 7.3.1.4-2..5), one check per Ta with Ta = 50 ms and the 5 ms
   floor (6.1.4.2-1, -4, 14.2-1, 14.2-4, B.1-1), a real STUN transaction per check with
   RTO ≥ 500 ms and retransmission of the same request (14.3-2, 14.3-4, 7.2.5.2.3-1, 7-1),
   a pair limit of 100, configurable (6.1.2.5-1, -2, -4, 19.5.1-1), checklist and ICE states
   including Completed and "all pairs done, none valid" (6.1.2.1-1, 6.1.3-1, 7.2.5.4-1,
   8.1.2-1, -2, -5), and failure of a nomination (7.2.5.3.4-2, -4, 7.3.1.5-3). Today's agent
   is pion's simplified one: every pair is pinged every 200 ms.
2. **WP-ICE-2: role conflict, both directions (M).** Answer 487 *or* process the request,
   never both; `>=` for the controlled case (7.3.1.1-3..6). Accept error responses:
   on 487 switch role, change the tiebreaker, re-queue the pair (7.2.5.1-1..4, 16.1-3,
   6.1.1-6); on another error response fail the pair (7.2.5.2.4-1). Tests must decode what
   the agent sends.
3. **WP-ICE-3: requests before the remote description (M).** Answer an authenticated-by-
   username Binding request as soon as local credentials exist, remember it, and run the
   peer-reflexive / triggered-check / nomination steps when the remote credentials arrive
   (7.3-5, 7.3-6, 5.3-4). Accept a username whose first part is the local ufrag (7.3-4).
4. **WP-ICE-4: PRIORITY and peer-reflexive candidates (M).** Send PRIORITY with the prflx
   type preference (7.1.1-2); take a remote prflx candidate's priority from the request
   (7.3.1.3-2) and do not pair it beyond the triggered pair (7.3.1.3-5); read
   XOR-MAPPED-ADDRESS from success responses, create local prflx candidates and the valid
   pair (7.2.5.3.1-1, 7.2.5.3.2-1); check the response's destination against the request's
   source and fail a non-symmetric pair (7.2.5.2.1-2, -3).
5. **WP-ICE-5: candidate priorities and foundations (M).** Unique local preferences per
   type, per interface and per TURN server, with an API to set them (5.1.2-1, 5.1.2.1-5,
   5.1.2.2-3, 5.2-6); RFC 8421 ordering (5.1.2.1-6, 5.1.2.2-2, 5.2-9, B.9-1); foundation from
   the base IP and the server (5.1.1.3-1, 5.2-5); reject priority 0 or > 2^31 − 1 and
   component outside 1..256 in every constructor (5.1.2-1, 5.1.2.1-7); drop redundant
   candidates, a relay equal to a host included (5.1.3-1, 5.1.1.2-9); component match when
   pairing (6.1.2.2-1); link-local rule in both directions (6.1.2.2-2).
6. **WP-ICE-6: lite agent (M).** No triggered checks from a lite agent: nominate on
   USE-CANDIDATE alone (7.3.2-1, 6.2-1, 8.2-1); keepalives from a lite agent (11-1);
   lite-to-lite selection and updated candidate exchange (6.2-2, 8.2-2, 8.2-3); one candidate
   per address (5.2-1); role tests with a lite peer (6.1.1-2, -3) and role redetermination
   when lite/full changes at a restart (6.1.1-5).
7. **WP-ICE-7: nomination rules (S).** Reject a nomination that is not followed with an
   error response (7.3.1.5-4). Decide 8.1.1-4: either keep the renomination behaviour and
   record it under "Decisions that change a claim", or select the highest-priority nominated
   pair when the peer did not send `NOMINATION`.
8. **WP-ICE-8: restart (S).** Refuse or regenerate when a restart would reuse the current
   ufrag / pwd (9-5); tests for the role across a restart (6.1.1-4, 9-6); optionally a new
   tiebreaker (16.1-4).
9. **WP-ICE-9: `ice2` and receive rule (S, after WP-ICE-1).** Write `a=ice-options:ice2`
   (10-1) once the agent earns it. Decide 12.2-1: accept data from any valid pair's remote
   (not only the selected one), or record the stricter rule as a decision. Optional: data on
   a valid pair before nomination (12.1-1), `ice-pacing` (14.2-2, -3), ICMP input
   (7.2.5.2.2-1).
10. **WP-ICE-10: tests for what is implemented but unproved (S).** Decode the agent's own
    requests and responses and assert PRIORITY, ICE-CONTROLLING / ICE-CONTROLLED, no
    USE-CANDIDATE when controlled, FINGERPRINT, XOR-MAPPED-ADDRESS, one tiebreaker, the 487
    code (7.1.1-1, 7.1.2-2, 7.1.3-1, -2, 7.2.4-1, -2, 7.3-7, -8, 7.3.1.2-1, 7.3.1.3-3, -4,
    16.1-2, 16.2-1); no second nomination (8.1.1-3); no data after Failed (12.1-4, 12.1.1-1).

Not gaps but decisions the owner should make explicit: gathering (5.1.1.x, 7.2.1) is `n/a`
only because the engine is sans-I/O. If "implements all of ICE" is to be literal, a gathering
layer (host enumeration rules, STUN / TURN transactions paced by Ta, keepalive of srflx
bindings, permissions for relayed checks) has to exist somewhere the project owns, with its
own audit; the engine also has no guard against loopback or IPv4-mapped local candidates.

## Bugs found

Fixed on `conf/ice-1-bugs`, each with the test named in its row: 1 to 13. Bug 6: the formula
was wrong and is fixed, but for priorities in 1..2^31-1 the old one put any two pairs in the
same order as the RFC's, so "order differs from a conformant peer" did not hold; only the
values did.

`conf/ice-3-checklist` is WP-ICE-1 (the checklist) and most of WP-ICE-4 and WP-ICE-5.

Decisions (kept behaviour that departs from the text, for the owner):

- 6.1.3-1 / 8.1.2-2: the RFC's states are `Agent::checklist_state()`. `Agent::state()` is the
  W3C transport state, where `Completed` means a nominated pair *and* no more candidates from
  either side; a nominated agent without both indications stays `Connected`.
- 7.3.1.5-3 / 7.2.5.3.4-4 (`conf/ice-14-controlled-nomination`): the RFC is the default on the
  controlled side too: the triggered check of a nomination failing fails the pair and the
  checklist. `FailedNomination::Retry` keeps the earlier behaviour (the pair only).
- 8.1.2-1: after a nomination the other pairs are no longer checked but stay in the list.
- 14.3: with the RFC's defaults (Rc 7, RTO 500 ms) an unanswered pair fails after 39.5 s. The
  checking timer (`disconnected_timeout + failed_timeout`, 30 s) no longer cuts that short: it
  fails the agent only once nothing is left in progress (`conf/ice-10-loss`; before, at 30 and
  40 % loss, the controlling agent failed 30 s in with its nomination's transaction open and
  the peer connected). `max_binding_requests` lowers Rc.

- 7.2.5.3.4-2 (`conf/ice-11-rfc-nomination`): the RFC is the default
  (`FailedNomination::FailChecklist`): a failed nomination fails the pair and the checklist, at
  the end of its transaction when it times out. `FailedNomination::Retry`
  (`with_ice_failed_nomination`), the default before, sends it again while the peer is heard
  from on the pair (within 30 s), then fails the pair and nominates the next valid one: under
  heavy loss a whole transaction's responses can be lost while the peer has accepted the
  nomination, and the RFC then leaves the peer connected (until its consent expires) and this
  agent failed. Every ICE default is now the RFC's.
- 7.3.1.5-4: a nomination the controlled agent does not follow (a lower libwebrtc `NOMINATION`
  value than the selected pair's) is answered with success, not an error: libwebrtc destroys a
  connection whose check is answered with an error, and the pair is one it still uses.
- 8.1.1-4 and 12.2-1: as the table says.

1. **Role conflict answers one request twice** (`rtci-ice/src/agent/mod.rs:1600-1614`,
   `:1760`, `:1822`). `handle_role_conflict` always sends a 487 and returns `Ok`; `handle_inbound`
   then answers the same transaction with a success response (and may learn a prflx
   candidate and send a triggered check). Reproduce: controlling agent, tiebreaker 500; feed
   an authenticated Binding request with ICE-CONTROLLING 100 from a known remote; drain
   `poll_write` and decode: two messages with the request's transaction id, one
   `BINDING_ERROR` 487 and one `BINDING_SUCCESS`. Expected: only the 487. With tiebreaker 100
   against 500: expected only the success, got both.
2. **A 487 from the peer is ignored** (`rtci-ice/src/agent/mod.rs:1674`). Two agents that
   both believe they are controlling, where the peer is a conformant implementation that
   answers 487 and keeps its role when it wins: this agent never switches from the response;
   it recovers only if the peer's own request reaches it. Reproduce: controlling agent sends
   a check; answer it with an authenticated 487; assert `is_controlling` is now false (it
   stays true and `handle_inbound` returns `ErrUnhandledStunpacket`).
3. **Equal tiebreakers leave both agents controlled** (`rtci-ice/src/agent/mod.rs:1653`):
   `>` where the RFC says "larger than or equal". Reproduce: controlled agent, tiebreaker 7,
   request with ICE-CONTROLLED 7: the role must become controlling.
4. **Binding requests are dropped until the remote description is applied**
   (`rtci-ice/src/agent/mod.rs:1690`). An offerer whose answerer starts checking before the
   answer is delivered (normal with trickle ICE) answers nothing; the peer's first checks
   time out and connection setup waits for retransmissions. Reproduce: agent with local
   candidates and no remote credentials; feed a Binding request whose USERNAME starts with
   the local ufrag and whose MESSAGE-INTEGRITY uses the local password; expect a success
   response, get `ErrPasswordEmpty`.
5. **The nominated pair is never given up** (`rtci-ice/src/agent/agent_selector.rs:269`).
   Once `nominated_pair` is set, every tick sends another USE-CANDIDATE request on it, with
   no count and no fallback. If the path dies between the successful check and the
   nomination, the agent ignores its other Succeeded pairs and fails after
   `disconnected_timeout + failed_timeout`. Reproduce: two remote candidates, both checks
   succeed; from then on drop everything to the higher-priority one; advance time: the agent
   reaches `Failed` instead of selecting the second pair.
6. **Pair priority formula** (`rtci-ice/src/candidate/candidate_pair.rs:191`):
   `(2^32 − 1)·MIN` instead of `2^32·MIN`. Reproduce: G = D = 2130706431 must give
   9151314442783293438; the code (and `test_candidate_pair_priority`) gives
   9151314440652587007. Ordering differs from a conformant peer for pairs such as
   (MIN 10, MAX 2^31 − 1) against (MIN 11, MAX 11).
7. **PRIORITY carries the wrong value** (`rtci-ice/src/agent/agent_selector.rs:316`, `:497`,
   `:147`). Reproduce: host candidate, one check; decode PRIORITY: expected
   110·2^24 + 65535·2^8 + 255 = 1862270975, got 2130706431. A conformant peer gives the
   peer-reflexive candidate it learns a host-level priority.
8. **An ICE restart with static credentials changes nothing**
   (`src/peer_connection/internal.rs:1682`, `rtci-ice/src/agent/mod.rs:938`). With
   `SettingEngine::set_ice_credentials`, `stage_ice_restart` stages the same ufrag / pwd.
   The restart offer carries the old credentials, the peer sees no restart, while this side
   has flushed its pairs. Reproduce: pin credentials, connect, `restart_ice()`,
   `create_offer`: the offer's `a=ice-ufrag` equals the previous one.
9. **A lite agent sends connectivity checks** (`rtci-ice/src/agent/agent_selector.rs:616-624`).
   A USE-CANDIDATE request to a lite controlled agent sets `nomination_pending` and sends a
   triggered check; the pair is selected only when that check is answered. Reproduce:
   lite agent, feed one authenticated request with USE-CANDIDATE, drain `poll_write`: a
   Binding request is among the output, and `get_selected_candidate_pair()` is `None` until
   it is answered.
10. **The controlled agent answers every request with a check of its own**
    (`rtci-ice/src/agent/agent_selector.rs:616-624`): the `else` branch runs for a request
    without nomination on a Succeeded pair too. Every consent check from the peer (every
    4 to 6 s per browser) costs an extra request / response pair. Reproduce: connected
    controlled agent; feed a plain authenticated Binding request on the selected pair; expect
    one datagram out (the response), get two.
11. **A Failed pair stays Failed on the controlled side when the peer checks it**
    (`rtci-ice/src/agent/agent_selector.rs:616-624`). The controlling selector resets the
    state and the request budget (`:410-417`); the controlled one sends one triggered check
    and leaves `state == Failed`, so if that single check is lost the timer never retries
    the pair. Reproduce: controlled agent, pair driven to Failed, then an inbound request on
    it: assert the pair is Waiting / In-Progress with a fresh budget.
12. **`COMPONENT_RTCP` is 0** (`rtci-ice/src/candidate/mod.rs:56`); the RTCP component is 2.
    Dead constant today, a wrong priority the day it is used. `CandidateConfig::default()`
    likewise builds component 0, outside 1..256.
13. **An ICE-CONTROLLED / ICE-CONTROLLING attribute appended after MESSAGE-INTEGRITY is
