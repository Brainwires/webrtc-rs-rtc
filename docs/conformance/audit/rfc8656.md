# RFC 8656 (TURN), client role: clause-level audit

Spec: RFC 8656, "Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal
Utilities for NAT (STUN)", February 2020 (obsoletes RFC 5766 and RFC 6156).
Audited: fork master 8916bc3, `rtci-turn/` (client only; there is no server), `rtci-shared/src/turn_framing.rs`.
Verdicts updated with the fixes on the `conf/turn-*` branches; the Code column names functions where the code moved.
Sections done: all (2 to 21). Sections 22 to 26 (IANA, IAB, changes, references) carry no requirement.

Scope notes

- `rtci-turn` is a sans-I/O TURN client. Neither `src/peer_connection` nor `rtci-ice` drives it: the
  crate is re-exported as `rtci::turn` and the application owns the socket, feeds
  `Client::handle_read`, and adds the relayed address as a relay candidate itself
  (`examples/trickle-ice-relay`, `tests/testenv/mod.rs`). Clauses about the socket, TLS / DTLS, DNS
  policy and the IP header are therefore `n/a` (application's job) unless the client takes the job on
  itself (it does resolve the server name, in `Client::new`). Since tcp-11 to tcp-17 the peer
  connection also runs the client itself for the configuration's servers (TCP, TLS, DTLS and
  plain UDP, `src/peer_connection/turn_streams.rs`); rows name that code where it decides.
- Server-only clauses are grouped, one `n/a` row per section and level.
- Level `DESC` marks behaviour the RFC states without an RFC 2119 keyword ("the client checks...",
  "it should consider...") that an implementation still has to do. They are counted separately.
- "env" in the Test column means the proof is a real-network environment test against coturn
  (`tests/testenv_*.rs`, `#[ignore]`d, run by `scripts/test-env/run.sh` in `test-env.yml`, Linux only),
  not a unit test.
- The unit tests in `rtci-turn/src/client/*_test.rs` drive the production `Client` through
  `sansio::Protocol` (`handle_read`, `handle_timeout`, `poll_write`, `poll_event`); the scripted
  `test_server.rs` only builds replies. They are not hollow. What they do not cover is listed per row.
- STUN-level rules the TURN client implements on its own (retransmission schedule in
  `client/transaction.rs`, 401 / 438 handling, response MESSAGE-INTEGRITY) belong to RFC 8489 and
  are only referenced here where RFC 8656 restates them. Observations on them are under "Notes for
  the RFC 8489 audit" at the end.

Code still following the obsoleted RFC 5766 / RFC 6156 (as audited; the citations now name
RFC 8656 and the listed features exist, except the RFC 8489 credential forms)

- `rtci-turn/src/lib.rs:5` describes the crate as RFC 5766 with RFC 6156; `proto/mod.rs:43,67`,
  `proto/chandata.rs:21`, `proto/channum.rs:30`, `proto/lifetime.rs:12`, `proto/relayaddr.rs:71`,
  `client/mod.rs:656,831,846` and `client/relay.rs:35` cite RFC 5766 sections.
- The feature set is RFC 5766 plus the RFC 8656 channel range: no ICMP attribute, no
  ADDITIONAL-ADDRESS-FAMILY / ADDRESS-ERROR-CODE (dual allocation), no Happy Eyeballs, and the
  long-term credential is the RFC 5389 one (MD5 key, MESSAGE-INTEGRITY with SHA-1, USERNAME in the
  clear; no PASSWORD-ALGORITHM, MESSAGE-INTEGRITY-SHA256 or USERHASH).
- Brought up to RFC 8656: channel numbers `0x4000..=0x4FFF` (`proto/channum.rs:22-24`,
  `client/binding.rs:11-12`), the 300 s permission lifetime comment (`client/relay.rs:22-24`), TURN
  stream framing (`rtci-shared/src/turn_framing.rs`).

## Gaps, in order of importance

1. **Allocation loss is never recognised (M).** RFC8656-5-6, 8.3-2, 8.3-4, 12.3-3, 7.4-1, 19-1.
   Give `Event` typed error codes (`AllocateError`, `CreatePermissionError`, a new
   `RefreshError` / `AllocationLost`, `ChannelBindError`) carrying the STUN code; on 437 to
   Refresh, CreatePermission or ChannelBind drop the relay and its bindings and report it; treat
   437 to a LIFETIME 0 Refresh as released; report a ChannelBind failure and, for 400, release the
   allocation. Read the error code on the first (unauthenticated) Allocate response, and accept a
   success response there (a server without authentication).
2. **Client-side permission and channel state does not expire or follow the server (M).**
   RFC8656-9-3, 12-4, 12-5, 11.4-2, 12.6-5, 12.3-2. Keep an expiry per permission (300 s from the
   last success) and per binding (600 s); refresh bindings from the timer, not only from a send;
   mark a permission lost when its refresh is refused or times out; keep a freed channel number
   out of use for 5 minutes; drop Data indications and ChannelData from peers without a
   permission; move bindings into `RelayState` so they end with the allocation (bug 1).
3. **Address families (M).** RFC8656-7.1-5, 7.3-1, 7.3-2, 7.3-3, 10.1-4, 12.1-2. Let the caller
   ask for an IPv6 relayed address (REQUESTED-ADDRESS-FAMILY), check the response's families,
   release an allocation the client cannot use, and refuse permissions and channel binds whose
   family differs from the relayed address.
4. **Allocate request options (S to M).** RFC8656-5-7, 5-8, 7.1-9, 7.1-10, 7.1-11, 7.1-12,
   11.1-3, 18.7-1, 7.3-7. SOFTWARE on Allocate and Refresh; an `AllocateOptions` with LIFETIME,
   DONT-FRAGMENT (and on Send, with the 420 fallback of 7.4-7), EVEN-PORT with R,
   RESERVATION-TOKEN (with the exclusion rules of 7.1-6, 7.1-8, 7.1-13); hand the
   XOR-MAPPED-ADDRESS and RESERVATION-TOKEN of the success response to the application.
5. **300 Try Alternate (S).** RFC8656-7.4-3. Read ALTERNATE-SERVER and either follow it (RFC
   8489 §10) or report it in the typed error.
6. **ICMP (S to M).** RFC8656-11.6-1, 11.6-2, 11.6-3, 11.4-3, 18.13-1. Define the ICMP attribute
   (0x8004), accept a Data indication carrying it without DATA, and raise an event with the peer
   address, type, code and error data.
7. **Dual allocation (M).** RFC8656-7.1-7, 18.11-1, 18.12-1, and the conditional rows 7.1-8,
   7.3-5, 7.3-6, 8.1-2, 10.1-5. ADDITIONAL-ADDRESS-FAMILY, two relayed addresses per allocation,
   ADDRESS-ERROR-CODE, per-family Refresh.
8. **RFC 8489 credentials in the TURN client (M).** RFC8656-6-2, 21.1.6-1. SHA-256 password
   algorithm with PASSWORD-ALGORITHMS / PASSWORD-ALGORITHM echo, MESSAGE-INTEGRITY-SHA256,
   USERHASH. (Shared with the RFC 8489 audit.) Done on branch `conf/turn-4-stun8489`, through
   `rtci_stun::long_term::LongTermCredentials`.
9. **Server discovery and Happy Eyeballs (M to L).** RFC8656-3.9-1, 3.9-2, 7.1-3. Take resolved
   addresses from the application instead of resolving in `Client::new`, or resolve A and AAAA
   and race them; SRV / NAPTR resolution (RFC 5928) and RFC 8155 discovery if the engine is to
   own them.
10. **Tests for what is implemented but unproved (S).** RFC8656-11.1-2 (decode a Send
    indication), 12-6 and 12.6-4 (inbound ChannelData before and without a binding), 12.5-1 and
    12.5-3 (a ChannelData datagram with an odd length leaves the client padded), 11.4-1, 5-9,
    7.4-4, 7.4-6, 7.4-9, 7.4-12, 3.1-3.

## Bugs found

1. **Channel bindings outlive their allocation.** `BindingManager` belongs to `Client`
   (`client/mod.rs:186`), not to `RelayState`, and is cleared neither when a relay is released
   (`client/relay.rs:570-573`) nor on a new Allocate. Reproduction: allocate, permit a peer,
   `send_to` and answer the ChannelBind (binding `Ready`); `Relay::close`, answer LIFETIME 0;
   allocate again within 5 minutes, permit the same peer, `send_to`. Expected a ChannelBind plus a
   Send indication; the client emits ChannelData on the old channel number, which the new
   allocation has not bound, so the server drops it silently until the binding is 5 minutes old.
2. **A lost release brings the allocation back.** `Relay::close` (`client/relay.rs:307-309`) only
   sends a Refresh with LIFETIME 0; the relay and its refresh timer stay until a success response
   arrives. If that Refresh and its one retry time out (`client/mod.rs:465-479`), or the server
   answers 437, the next periodic refresh (`client/relay.rs:151-178`) sends the old non-zero
   lifetime and keeps alive the allocation the application released. Reproduction: allocate,
   `relay.close(now)`, answer nothing, drive `handle_timeout` to `now + lifetime / 2`: a Refresh
   with LIFETIME 600 goes out.
3. **A 437 (or any error) to a Refresh is swallowed and the dead allocation is refreshed for
   ever.** `handle_refresh_response` (`client/relay.rs:533-548`) returns `Err` to the caller of
   `handle_read` and raises no event; the relay stays in `Client::relays`, `send_to` keeps
   succeeding locally, and a Refresh goes out every half lifetime. Reproduction: allocate, drive
   to the refresh, answer it with a signed 437: assert no event, `client.relay(addr)` still `Ok`,
   and another Refresh at the next deadline.
4. **ChannelData length wraps at 64 KiB.** `ChannelData::write_header`
   (`proto/chandata.rs:91-92`) writes `data.len() as u16` and `Relay::send_to` puts no limit on
   the payload (`MAX_DATA_BUFFER_SIZE` is unused, `client/mod.rs:70`). Reproduction: on a bound
   channel `send_to` 65 540 bytes; the header says length 4 and the message carries 65 540 bytes,
   which over TCP / TLS desynchronises the stream for every later message. Expected an error.
5. **Running out of channel numbers fails the send instead of falling back to a Send
   indication.** `Relay::send` (`client/relay.rs:222-229`) returns `Error::Other("Addr not
   found")` when `BindingManager::create` finds no free number, and bindings are never removed, so
   the 4097th distinct peer address (ports count) of a client's lifetime can never be sent to.
   Reproduction: permit one IP, `send_to` 4096 ports on it, then one more.
6. **The first Allocate response is taken for a 401 whatever it is.**
   `handle_allocate_response` (`client/mod.rs:748-766`) checks neither class nor error code. A
   success response (a server that needs no authentication, RFC 8656 §7.2 step 1) is reported as
   `AllocateError(attribute not found)` while the server holds the allocation, which nothing
   refreshes or deletes, and a later `allocate` on the same 5-tuple gets 437. A 300, 403, 442,
   486 or 508 loses its code the same way. Reproduction: answer the first Allocate with a success
   carrying XOR-RELAYED-ADDRESS and LIFETIME.
7. **A malformed Allocate success leaves an orphan allocation and no event.**
   `relayed.get_from(&response)?` and `lifetime.get_from(&response)?` (`client/mod.rs:823,828`)
   return from `handle_read` after the transaction was removed (`client/mod.rs:378`): the caller
   of `allocate` never gets `AllocateResponse`, `AllocateError` or `TransactionTimeout` for its
   id. Reproduction: answer the authenticated Allocate with a signed success lacking LIFETIME,
   then drive time: no event ever.
8. **`update_credentials` documents a username change on a live allocation as correct.**
   `client/mod.rs:652-688`. RFC 8656 §5 has the server reject a request whose username differs
   from the one that created the allocation with 441, so rotating time-limited (REST) credentials
   this way loses the allocation at the next Refresh, and bug 3 then hides it. Reproduction
   against coturn: allocate with user A, `update_credentials` with user B, `refresh_allocations`.
9. **A refused permission refresh is invisible.** For a refresh (`peer_addr_opt == None`)
   `handle_create_permission_response` (`client/relay.rs:423-450`) drops an error response
   without an event and leaves every permission `Permitted`. One peer address of another family
   (10.1-4) or one the server forbids (403) therefore fails the whole batch of up to 16 at every
   refresh, the server's permissions lapse after 300 s, and the client keeps sending.
   Reproduction: permit an IPv4 and an IPv6 peer on an IPv4 allocation, drive 120 s, answer the
   refresh with 443, drive on: no event, `send_to` still `Ok`.

## Notes for the RFC 8489 audit (TURN client's own STUN machinery)

Status on branch `conf/turn-4-stun8489`: none of the four notes below holds any more. The
client sends on the RFC 8489 §6.2 timer it shares with `rtci-stun` (500 ms, doubling, Rc 7,
Rm 16, Ti 39.5 s, RFC 6298 estimate, configurable); a 438 to the authenticated Allocate is
retried once; every received message goes through `rtci_stun::validated::Validator`
(FINGERPRINT, integrity, unknown comprehension-required attributes, nothing read after the
integrity attribute); and the user name, realm and password go through OpaqueString in
`LongTermCredentials`. The rows are in `rfc8489.md`.

- `client/transaction.rs:14-15`, `client/mod.rs:69`: default RTO 200 ms (RFC 8489 §6.2.1 SHOULD
  be at least 500 ms), doubling capped at 1600 ms, 7 transmissions, and the transaction ends one
  interval after the last one (about 7.8 s in all) where the RFC waits Rm x RTO; the comment
  table at `client/mod.rs:119-127` describes the RFC schedule, not this one. Over TCP it is Ti =
  39.5 s, sent once (tested).
- A 438 to the authenticated Allocate is not retried (`client/mod.rs:809-818`); Refresh,
  CreatePermission and ChannelBind retry once (tested).
- Responses to signed requests must carry a valid MESSAGE-INTEGRITY, except an unsigned 401 or
  438 (`client/mod.rs:959-970`, tested); FINGERPRINT on inbound messages is not checked; unknown
  comprehension-required attributes in responses are not checked.
- The realm from the 401 replaces the configured one (`client/mod.rs:759`); username, realm and
  password are not passed through OpaqueString / SASLprep in this crate.
