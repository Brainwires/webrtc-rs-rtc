Spec: RFC 3264, June 2002 (updated by RFC 6157, RFC 8843 / 9143). Audited at fork master 8916bc3.
JSEP (RFC 9429) profiles this model: addresses and ports are ICE's, so the port-change and multicast
clauses are `n/a`; the SIP capability exchange of section 9 is not used.

## Gaps, in order of importance

1. **Default direction (S).** RFC3264-6.1-4 (shared with rfc8866.md 6.7-2).
2. **Session version (S).** RFC3264-8-2, 8-3 (shared with rfc9429.md 5.2.2-1).
3. **Mirror the offer's t= (S).** RFC3264-6-4.
4. **Validate remote re-offers (M).** RFC3264-8-6, 8.3.2-2, 6.1-2, 8.3.3-1: fewer m= lines than before,
   a payload type remapped to another codec, a media type that changed for a mid.
5. **Asymmetric payload types (M).** Closed (jsep-71): RFC3264-5.1-8, payload types per direction.
6. **Receive before the answer (M).** RFC3264-5.1-16, 5.1-17.
7. **ptime and bandwidth (M).** RFC3264-5.1-14, 6.1-15, 6.1-16, 6.1-20, 6.1-21, 7-3.
8. **Formats beyond the offer in answers, send-only / receive-only codec lists (M).** RFC3264-6.1-7, 5.1-7.
9. **Offer creation in the wrong state (S).** RFC3264-4-3.
10. **Tests only.** The `untested` rows, notably 6-6, 8.3.2-3, 6.1-13.

- **RFC3264-6.1-4:** an offered m= section with no direction attribute is not treated as sendrecv; see

- **RFC3264-8-2 / 8-3:** the o= version does not increment by one; see rfc9429.md (RFC9429-5.2.2-1).
- **RFC3264-6-4:** the answer's `t=` line is always `t=0 0`. Reproduce: remote offer with
  `t=3034423619 3042462419`; the answer still says `t=0 0`.
