# Performance ledger

Every performance decision that was **measured** and then accepted, and every measured
alternative that was refused, one row each, newest first. A refused alternative is a decision
too: its row says what it would have cost. Figures are quoted from the source named in the row,
on the tree that source measured; where two sources disagree the row uses the one measured on
the later tree and says so.

Rules for branches:

- A branch that moves a measured figure (a capacity-instrument cell, a capacity-cap bound, a
  criterion benchmark, RTCP volume, a CI job's time) adds its row here **in the same branch**:
  status `queued` with the branch name while it is not on master, `master` once it is (the
  integrator flips it), with the files and tests that state or guard it.
- Its CHANGELOG entry under `[Unreleased]` carries a line `Performance: <row id>`.
  `scripts/check-performance-ledger.py` (the `Test inventory` job of `cargo.yml`) fails on a tag
  without a row, on a `master` or `rejected` row that names no file of the repository or names one
  (or a `file.rs::test`) that does not exist, and on a `queued` row without its `conf/...` branch.
- A micro-benchmark made slower on purpose also needs an entry in
  `benches/accepted-regressions.toml` naming the row (see "How to measure").

Status: `master` (on master), `queued` (on the branch named, not on master yet; train 34,
`conf/train-34`, was open when this ledger was written), `rejected` (measured, not taken; the
default it was compared with is on master). "Cell" names are the capacity instrument's
(`tests/capacity_instrument.rs`); the reference cell is `cap/paced/gap300/up/q300/rl0`: the
default chain, a receiver with the 300 ms gap bound, 2.5 Mbit/s cut to 300 kbit/s for 20 s
behind a 300 ms queue. `±` is the 95 % half-width of the per-seed difference as the source states
it. "Under the cap" is the mean target while the cap lasts; "15–25 s after" the mean target in
that window after the cap lifts; "slow recoveries" are calls not back at 1000 kbit/s within 20 s.

## How to measure

**Behaviour through a capacity collapse: the capacity instrument.** A simulated call through a
collapse, cell by cell, with a committed baseline (`tests/fixtures/capacity-instrument-baseline.tsv`),
tripwires that run on every pull request (job "Capacity instrument (release ensemble)" in
`cargo.yml`, row `instrument-2-ci`), and the two-tree comparison with the merge-point rule
(`capacity-compare.yml`, by hand) for any change to congestion control, pacing, retransmission or
RTCP timing. Everything about it, including when to re-record the baseline, is in
[`capacity-instrument.md`](capacity-instrument.md); most rows above quote its figures.

**Per-operation cost: the criterion micro-benchmarks, compared on every pull request.** The job
"Benchmarks compared with the base" of `.github/workflows/bench.yml` builds the pull request and
its base on the **same runner** (`scripts/bench-compare.sh`: a second worktree with its own target
directory) and runs every bench of `rtci-stun`, `rtci-rtcp`, `rtci-turn`, `rtci-rtp`, `rtci-sdp`,
`rtci-media`, `rtci-srtp`, `rtci-dtls` and `rtci-interceptor` in rounds that alternate between the
trees (base, head, then head, base), with a 1 s warm-up and 2 s of measurement each; figures from
two different runs are never compared, because hosted runners differ by up to 2× between machines.
`scripts/bench-compare.py` (unit tests in `scripts/test_bench_compare.py`) takes the head's median
over the base's per bench, with the spread of the per-round ratios, and fails the job when a bench
is slower than its base **in every round** by more than 20 % and by more than 25 ns in absolute
terms. These were set from five base==head runs (45658476946, 45658485287, 45658494781,
45658504156, 45658513288; 99 benches, 10 rounds each): single rounds ranged from 0.85 to 1.40
(the noisiest are the sub-100 ns marshal and STUN attribute benches and the
`Interceptor/NackResponder/buffer` bench, 0.92–1.28), but the lowest round of a bench in a run,
which is what the rule looks at, never exceeded 1.053; benches above 1 µs stayed within
0.97–1.03. The gate therefore detects a regression of 20 % (and 25 ns) or more with about four
times the observed noise as margin; a smaller one shows in the table but does not fail. A second
rule (row `bench-2`) closes the floor's blind spot: over at least four rounds of each tree, a
bench is slower when the head's fastest round is beyond the base's slowest by more than 5 % and
3 ns, so the noise band is the base's own spread on that runner; a bench separated after the two
rounds is run again alone for four more alternating rounds (`BENCH_CONFIRM_ROUNDS`) before the
verdict. Train 36's pacer regression (×1.07 to ×1.30) passed the first rule for twelve rounds
because 25 ns was reached only on fast runners. A 46× DTLS
setup cost is caught by a wide margin (mutation `mut/perf-1-scrub`, run 45665811195: ratio 57.9, both rounds 57.2–58.6; the key-erasure branch's bulk scrub, ×3.9 and ×5.7, is caught too, run 45665836618). The same
runs show why the comparison stays inside one job: the DTLS handshake measured 221 µs on one
runner and 330 µs on another for identical code, and the key-erasure branch saw two runs on
different runners differ by about 18 % on per-packet figures. A
regression that is accepted is a ledger row plus an entry in `benches/accepted-regressions.toml`
(bench name or glob, the ratio it accepts, the row id); the job prints exactly that when it fails,
and lists entries that no longer match anything as stale once the base has moved. On a push to
master the once-per-merge run still publishes the figures to the history (`docs/benchmarks` on the
benchmark data branch) with its 110 % alert. To measure a branch before queueing it, dispatch
`scripts/bench-compare.sh <base sha> <crate>:<bench> ...` through `agent-test.yml`.
